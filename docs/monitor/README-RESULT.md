# 장애대응 결과

## 1. 장애 개요

### 1.1 장애 정보
- **발생일시**: 2025년 1월 (부하 테스트 중 발견)
- **장애 수준**: Major (성능 저하로 인한 사용자 경험 악화)
- **영향 범위**: 인기상품 조회 API 전체
- **복구 완료**: 2025년 1월 (캐싱 및 인덱스 적용 후)

### 1.2 장애 현상
- **인기상품 조회 API 심각한 성능 저하**
    - 평균 응답시간: 4초 (목표: 200ms 이하)
    - 최대 응답시간: 8초
    - Slow Query 발생으로 데이터베이스 부하 급증

## 2. 장애 원인 분석

### 2.1 근본 원인
- **데이터베이스 성능 문제**
    - 대용량 데이터 (주문: 10만건, 주문아이템: 100만건, 상품: 1000건)에서 인기상품 통계 쿼리 최적화 부족
    - 적절한 인덱스 부재로 인한 풀 테이블 스캔 발생
    - 캐싱 시스템 미적용으로 매번 DB 조회 수행

### 2.2 성능 분석 결과
- **플레임 그래프 분석**: 인기상품 조회 메서드에서 CPU 사용량 집중
- **호출트리 분석**: 데이터베이스 쿼리 실행 시간이 전체 응답시간의 95% 이상 차지
- **메서드 분석**: `getTopSellingProducts()` 메서드가 주요 병목 지점으로 확인

## 3. 장애 대응 과정

### 3.1 장애 감지 및 초기 대응
1. **장애 감지**: K6 부하 테스트를 통한 성능 이슈 발견
2. **장애 분석**: 플레임 그래프, 호출트리, 메서드 분석을 통한 병목 지점 파악
3. **대응팀 구성**: 개발팀 주도로 긴급 성능 개선 작업 착수

### 3.2 임시 조치
- 인기상품 조회 API 호출 빈도 제한 (임시)
- 데이터베이스 커넥션 풀 조정

### 3.3 근본적 해결책 적용

#### 3.3.1 Redis 캐싱 시스템 도입
```java
@Cacheable(value = "popularItemsCache", key = "#from + '_' + #limit", cacheManager = "redisCacheManager")
public List<PopularItemsResult> getPopularItems(int from, int limit) {
    return orderItemRepository.findPopularItems(from, limit);
}
```

#### 3.3.2 데이터베이스 인덱스 최적화
```sql
-- 인기상품 조회 최적화 인덱스
create index idx_ordered_at_item_id on order_item(ordered_at, item_id);

-- 주문 상태 조회 최적화 인덱스
```

## 4. 개선 결과

### 4.1 성능 개선 지표

| **항목** | **개선 전** | **개선 후** | **개선률** |
|---------|-----------|-----------|----------|
| 평균 응답시간 | 4,000ms | 2.46ms | **99.9%** |
| P50 응답시간 | - | 1.45ms | - |
| P90 응답시간 | - | 4.21ms | - |
| P95 응답시간 | - | 6ms | - |
| 최대 응답시간 | 8,000ms | 640.57ms | **92.0%** |
| 성공률 | - | 100.00% | - |

### 4.3 시스템 안정성 향상
- **Checks**: 100.00% (모든 테스트 성공)
- **데이터베이스 부하**: 대폭 감소 (Redis 캐시 히트율 95% 이상)
- **사용자 경험**: 실시간 인기상품 조회 가능

**새로운 아키텍처의 기술적 우위**
- **Redis Sorted Set 활용**: O(log N) 복잡도로 빠른 순위 조회
- **Union 연산 최적화**: 3일치 데이터를 메모리에서 고속 합산
- **스마트 캐싱**: 1시간 TTL로 메모리 사용량 자동 관리
- **하이브리드 조회**: Redis(집계) + DB(상세정보)로 최적화
